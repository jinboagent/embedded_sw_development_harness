# embedded-agent-kit

**English | [简体中文](README_zh.md)**

**一套与 AI 智能体协同开发软件的流程工具包 —— 提取自一个真实的硬件项目：多个 LLM
智能体在数月的会话中开发、测试并交付了 ESP32 固件。**

你正准备和编码智能体一起构建一个项目。它们快、不知疲倦、而且无状态 ——
它们会在会话之间忘记规则，不加证明就宣称"已验证"，留下的 git
历史几周后没人能审计。这个工具包就是解决这些问题的操作手册：一组文件，把智能体的行为从"依赖聊天记录"变成"依赖宪章"。

把文件夹拷进去，填好占位符，装一个钩子 ——
你的智能体就继承了同样的纪律：一个六阶段固件项目因此在 500
多项通过的检查之下交付，每一个结论都有运行记录背书。

## 问题所在（一段话说清）

AI 编码智能体缺的不是智力，而是*制度*。人类团队靠入职文档、评审习惯和口口相传的经验积累规则；智能体团队什么都没有
——
每次会话都从它当前读到的内容开始。没有结构，你就会得到：活在聊天记录里的规则（下次会话就消失）、"在我机器上能跑"式的验证结论、`fix
stuff` 式的提交、悄悄偏离代码的架构图，以及一条没人敢动的主分支。这个工具包的每一个元素，都源于源项目里真实发生过的一次失败，而对应的修复经受住了数月的检验。

## 使用它的收益

- **会话开局即聪明。** 新智能体（或新的人类协作者）打开仓库，规则已经在那里 ——
  没有入职聊天，也没有智能体之间、月份之间的规则漂移。源项目里，四个不同的智能体遵循同一部宪章，却从未共享过任何聊天记录。
- **"已验证"有了含金量。** 每个结论都指向一份运行记录；每个提交的 Verification
  段落都可复现。你不必再反复争论"它到底能不能跑"。
- **历史能回答问题。** 承诺过什么、落地了什么、为什么、证据在哪 ——
  一年后依然可以从 FEATURES 索引、分支清单和四段式提交里得到答案，无需考古。
- **静默漂移变成响亮失败。** 与代码不符的图、漏掉 Why 或 Verification
  的提交 —— 机械检查会抓住它们，不靠任何人记着。
- **更便宜、更专注的智能体会话。** 分层加载把上下文花在当前那份规格上，而不是整个档案库 ——
  更小的提示词，更少的"又忘了规则"循环。
- **无锁定，无基础设施。** 纯 markdown、一个 shell 钩子、一个 Python
  脚本。任何会读文件的智能体都能用它；随时离开，文件全归你。
- **经过实战检验的流程。** 不是理论：这套流程带着六阶段固件走到 500+
  项通过的检查，每个结论都有转录背书，还经受了一次独立的智能体评审。

## 方法论 —— 七条原则

1. **智能体需要宪章，而不是聊天历史。** 规则活在小的、稳定的、每次会话都加载的文件里
   （`agent-context/` + `harness/00-global-context/`）。规则若重要，就在文件里；在文件里，就会被加载。
2. **拿不出证据，就当没发生。** "已验证"意味着 `harness/02-knowledge/`
   下有一份运行记录 —— 别的都不算数。提交信息引用命令与计数，运行记录证明它们。
3. **一个功能，一条分支，一份清单。** 每条分支携带 `BRANCH`
   清单（范围、验收标准、变更日志）；每次 squash
   合并在 `FEATURES` 索引落一行。历史保持为审计轨迹，而不是流水账。
4. **提交是结构化文档。** `type(scope): summary` 加上 What / Why / How /
   Verification 四段 —— 由 git
   钩子强制执行，因为源项目里纯靠自觉的约定几周就腐化了。
5. **架构图会静默腐烂 —— 所以要登记。** 每张 ASCII 图都有 ID、哈希和一个在漂移时让构建失败的检查器。
6. **状态是指针，不是维基。** `status/LATEST.md`
   指向最新快照；快照只追加、不修改。
7. **上下文是预算。** 智能体加载宪章（小、常驻）加当前正在改的那份规格
   —— 不加载档案库，不加载证据库，不加载停车场。

```
          │  目标 · 评审 · 唯一的部署密钥
          ▼
┌──────────────┐  每次会话加载      ┌─────────────────────────────┐
│ 编码智能体   │◄─────────────────► │ harness/00-global-context/  │
│              │                    │ 规则 · 构建 · git 工作流    │
│              │   按任务匹配加载   ├─────────────────────────────┤
│ 改代码       │◄─────────────────► │ harness/01-features/<stage>/│
│ 跑测试       │                    │ 规格说明 + 验收标准         │
└──────┬───────┘                    └─────────────────────────────┘
       │  每个结论都需要一份运行记录
       ▼
┌──────────────┐   落盘运行记录     harness/02-knowledge/
│ 测试门禁     │──────────────────► evidence-<feature>-<date>/
└──────┬───────┘   + 过程报告        <feature>-<date>.md（"为什么"）
       ▼
 四段式提交 ─► BRANCH 清单 ─► squash 合并 ─► FEATURES 索引
```

这个循环就是产品本身：规则进，证据出，能自我解释的历史。智能体从不"记住"一条规则
—— 它重新读一遍；从不"相信"一个修复 —— 它重新跑一遍。

## AI 时代特有的：文档驱动开发

当执行者是 LLM 时，文档就不再是"文档"，而成为**编程接口**。这是整套工具包背后的信条：

- **瓶颈从生成移到了验证与上下文。** 智能体几秒写完代码，并流利地宣称正确。产出是乘法式的
  —— *模型能力 × 上下文质量* ——
  强模型配上零上下文，产出的有用代码也是零。杠杆率最高的工程动作不再是写代码，而是写出代码将要从中生成的那些文档。（腾讯
  QQ 音乐团队独立得出了同样结论，并据此构建了一整层"Harness
  Engineering"工程治理 —— 见下文对比。）
- **文档是可执行的输入。** 智能体读规格不是为了找感觉 ——
  它加载规格、对着规格做计划、并被规格打分。所以文档必须机器可消费：验收标准是可检查的规则，错误码是表格，状态机是登记过的图，规则是常驻的小文件。这个工具包的模板长成这个样子，原因就在这里。
- **门禁设在错误最便宜的位置。** 错误的假设：在规格期值一次修改，在编码期值一次重写，在合并后就是一次事故。所以下面每个阶段都以*机器校验*的门禁收尾（钩子、检查器、测试门禁、人工部署密钥），而不是靠约定
  —— 约定会腐化，门禁不会。
- **知识只有写下来才能复利。** 活在聊天上下文里的教训随会话而死。归档成文档
  —— 一份过程报告、一条学习日志 ——
  它就成为下一个会话会重读的资产。每一次纠正的循环都应该终结于一份文档。

<!-- chart-id: CH-readme-zh-04 rev1 -->
```
 意图 ─► 规格 ─► 智能体 ─► 代码 ─► 门禁 ─► 证据 ─► 历史
             ▲                                     │
             └──────── 教训沉淀为文档 ◄────────────┘
```

上面这个循环就是全部思想：意图变成文档，文档驱动生成，门禁索要证明，证明成为历史
—— 而教训作为新文档流回。

## 一个功能的一生

<!-- chart-id: CH-readme-zh-02 rev1 -->
```
 提案 / 规格                    开分支                 实现
┌────────────┐    评审通过    ┌──────────────┐    编码    ┌──────────────┐
│ 功能模板   │──────────────► │ feature/<x>  │───────────►│ 代码 + 测试  │
│            │                │ + BRANCH 清单│            │ 对照验收标准 │
└────────────┘                └──────────────┘            └──────┬───────┘
                                                                 │ 门禁转绿，
                                                                 ▼ 证据落盘
 FEATURES 行    ◄────────  squash 合并  ◄────────────────────────┘
 （索引更新）               （四段式提交说明）
```

除了这条路径，没有任何东西能落到 main 上 —— 清单加索引意味着一年之后，对任何一行代码你都能回答："当时承诺了什么、证明了什么、运行记录在哪。"

逐阶段看，每一步都把一份文档转换为下一份 —— 智能体从不凭记忆或感觉工作：

| 阶段 | 驱动它的文档 | 收尾它的门禁 | 由谁强制 |
|---|---|---|---|
| 1. 想法 → 提案 | 功能提案：想法、理由、**编号的决策及决策人**、风险 | 决策收敛（"与产品所有者共同锁定"） | 人工评审 |
| 2. 提案 → 规格 | 用模板写功能规格：验收标准、错误码、测试用例**先于代码写出** | 规格锁定；开分支 + 实例化清单 | 智能体预检清单 |
| 3. 规格 → 代码 | 规格的验收标准 + 宪章（编码规则、分层、错误码区间） | 单元 + 契约测试转绿 | 测试套件 |
| 4. 代码 → 证明 | 清单中的验证计划 | 回归/硬件门禁转绿，运行记录落盘 | 门禁执行器 + 证据规则 |
| 5. 证明 → 历史 | 四段式提交信息 | 结构校验通过 | `commit-msg` 钩子 |
| 6. 历史 → 记忆 | 过程报告 + 学习日志条目 | 报告存在且指向证据 | 会话仪式 |

这些门禁被刻意设计得运行成本低、无从争辩：阶段 1、2 花一次评审，阶段 3、4
花一条命令，阶段 5 零成本（钩子反正会跑），阶段 6 花五分钟。而昂贵的失败模式
—— 错误的前提、未证明的结论、不可审计的合并、丢失的教训
—— 每一个都在拦住它最便宜的阶段被拦截。

## 如何使用本仓库

### 拿走它（一分钟）

把文件夹拷进新项目 —— 不安装任何东西，没有后台进程：

```bash
cp -r embedded-agent-kit/{agent-context,git-workflow,harness,templates,tools} /path/to/project/
```

或者克隆本仓库后删掉 `.git`。先浏览 `templates/`，删掉项目用不上的（Unity C
测试不适用于 Python 服务；`bug_check/` 是可选的）。

### 一次性设置（每个项目）

1. 填好每一个 `{{PLACEHOLDER}}` —— 每个模板顶部都列出**编辑要点**。
2. 按骨架撰写 `AGENTS.*.md` + `CLAUDE.md`；保留"保持同步"的头部。
3. 每个克隆安装一次提交钩子：`git config core.hooksPath git-workflow/githooks`
4. 用 `tools/chart-registry.template.md` 建立 `docs/chart-registry.*.md`，然后
   `python tools/check_charts.py --scan` 收编已有图表。
5. 写第一份 `status/status-<date>-<slug>.md` + `status/LATEST.md`。
6. 撰写入口文件所承诺的文件：根 `README.md`、`docs/quickstart.md`、`docs/tostudy.md`（都在 `templates/`）。
7. 在 `FEATURES.*.md` 登记第一个基线；按 `git-workflow/feature-branch-policy.md` 切功能分支。
8. 如果按 ID 跟踪缺陷，用 `templates/bug-tracking.template.md` 建立 `bug_check/README.md`。
9. 若项目是 C 固件，适配 `templates/unit_test_template.md`（Unity C）；否则换成你技术栈的等价物。
10. 按 `agent-context/ignore-files.md` 设置忽略文件（并把
    `templates/.gitignore.template.md` 拷为 `.gitignore`）。
11. 把想要的 `skills/` 装进你智能体的技能目录（见 `skills/README.md`）。
12. 在任何东西公开之前，执行
    `harness/00-global-context/publishing_privacy.template.md` 中的隐私审计块。

### 日常节奏

- **开始会话** —— 读 `status/LATEST.md`（进展到哪）、在途的 `BRANCH`
  清单（承诺了什么）、以及你要改的那份规格。智能体自动获得前两层；人类读两个文件就够。
- **工作过程中** —— 宪章的规则生效（编码规则、分层、错误码区间）；改了登记过的图，就更新注册表行并保持
  `check_charts.py` 干净；在下任何结论之前先跑测试。
- **结束会话** —— 把过程报告 + 证据归档到 `harness/02-knowledge/`，写状态快照并移动
  `LATEST.md` 指针，通过钩子提交。
- **合并功能** —— 门禁转绿 → 带四段式说明 squash 合并 → 加 FEATURES 行 → 关闭清单的合并记录。

### 按需查找

| 你想…… | 去哪 |
|---|---|
| 开始一个新功能 | `harness/01-features/feature_template.md` → 切分支 → `git-workflow/BRANCH.template.md` |
| 知道某个东西为什么存在 | `harness/02-knowledge/` 的过程报告（每次会话一份，附运行记录） |
| 证明某个东西能跑 | `harness/02-knowledge/EVIDENCE-CONVENTIONS.md`，然后跑门禁命令 |
| 改一张图 | 标记 + 注册表行 + `python tools/check_charts.py` |
| 修一个缺陷 | `templates/bug-tracking.template.md` 索引；`fix(scope): … (B1)` 提交 |
| 公开发布 | `harness/00-global-context/publishing_privacy.template.md` 的审计块 |
| 给新智能体入职 | `agent-context/AGENTS.template.md` + `CLAUDE.template.md` |

## 工具箱里有什么

| 文件夹 | 它给你什么 |
|---|---|
| `agent-context/` | AGENTS/CLAUDE 入口骨架、智能体记忆模板、忽略文件/上下文分层策略 |
| `git-workflow/` | 功能分支策略、BRANCH/FEATURES 清单模板、提交标准 + 强制钩子 |
| `harness/` | 三层树：宪章、功能规格、过程报告 + 证据规则 |
| `templates/` | 填空文件：功能规格、Unity C 测试、状态快照、测试 README、quickstart、学习日志、根 README、`.gitignore`、缺陷跟踪 + 修复报告 |
| `tools/` | 图表注册表检查器 + 注册表模板（机械化的图表治理） |
| `skills/` | 智能体技能（标准 SKILL.md 格式）：tmux-esp32 工作流、图表治理、证据门禁、图表生成、Medium 文章、发布前审计 —— 拷进任何智能体的技能目录即可 |

## 为什么是这样设计的

| 决策 | 原因 |
|---|---|
| Markdown 文件，而不是工具/框架 | 智能体天然读文件；零安装、零锁定、可在 git 中 diff |
| 钩子强制的提交，而不是约定 | 源项目审计了 47 个自由格式的提交：46 个漂移了。约定会腐化，39 行的 shell 钩子不会 |
| 带 `{{placeholders}}` 的模板，而不是脚本 | 作者权在你手里；工具包塑造判断力，不把判断力自动化掉 |
| 只追加的状态与证据 | 可以编辑的历史是不可信的历史；修正 = 新增条目，不是重写 |
| 证据规则（"没有转录就没发生"） | 智能体表达信心很流利；运行记录是唯一不膨胀的货币 |
| 图表注册表 + 检查器 | 图的漂移在误导人之前是不可见的；一个哈希让它变成构建失败 |
| 小宪章、分层加载 | 上下文是稀缺资源；这个设计刻意地花费它 |

## 出处

提取自一个 ESP32-S3 BLE 桥接固件项目：多个 LLM
智能体（ZCode、Claude、DeepSeek、Qwen）在这套工作流下建成了六个阶段的功能
—— 每次合并由硬件测试把门，每个结论携带运行记录。工具包随后经过另一个智能体的独立评审，其增补（缺陷跟踪、quickstart、学习日志和五个缺陷修复）经复审后并入。"文档驱动开发"一章是在对照腾讯
QQ 音乐的 Harness Engineering 文章（2026）—— 一次独立的原则趋同，平台规模
—— 的过程中定稿的。把它当作经过实战检验的流程，而不是理论。
